# v1 5단계 — 데모 시딩 규모와 좌석맵 응답 측정

| 항목 | 내용 |
|---|---|
| 측정일 | 2026-10-05 |
| 대상 | `seed` 프로필 시더(`DemoDataSeeder`), `GET /api/games/{id}/seats` |
| 환경 | 로컬 MySQL 8.4 (Docker), `--spring.profiles.active=local,seed`, `rewriteBatchedStatements=true` |
| 테스트 | `DemoDataSeederTest` (Testcontainers MySQL, 같은 시더 실행) |

## 시딩 규모

| 항목 | 값 |
|---|---|
| 구역 (section) | 30 — 중앙석 / 1루 필드석 / 3루 필드석 / 1루 외야석 / 3루 외야석 x A~C x 앞·뒤 2블록 |
| 좌석 (seat) | 22,536 (구역별 행 16~24, 블록당 열 24~60) |
| 경기 (game) | 5 (구단명은 실제 KBO 10개 구단, 일정은 데모 임의 값, 예매 오픈 2개) |
| 경기별 좌석 (game_seat) | 112,680 = 22,536 x 5 |

좌석 배치 근거: 중앙석은 뒤 층일수록 행이 많고, 외야석은 열이 길다. 구역 이름 체계는 프론트 지도가
해석하므로 시더에서 바꾸면 안 된다.

## 시딩 시간

| 실행 | 구역·좌석 | 경기(좌석 복제 포함) | 합계 |
|---|---|---|---|
| 로컬 DB, 앱 기동 시 1회 | 584 ms | 1,511 ms | 2,095 ms |
| 테스트 (Testcontainers) | 646 ms | 1,314 ms | 1,961 ms |

구역·좌석은 좌석을 구역별 JDBC 배치(500건 청크)로 넣는다. 경기는 생성할 때마다 현재 존재하는 좌석 전부에
대해 `game_seat`을 만들어서(2단계 설계), 경기 5개를 만들면 좌석 복제가 5번 일어나는 게 시간의 대부분이다.

## 좌석맵 응답

`GET /api/games/1/seats` (좌석 22,536석, 로컬, 5회 측정)

| 회차 | 응답 시간 | 크기 |
|---|---|---|
| 1 (워밍업) | 228 ms | 3.14 MB |
| 2~5 | 115~129 ms | 3.14 MB |

쿼리는 `GameSeat`-`Seat`-`Section` join 한 번이다(3단계에서 N+1을 막은 형태 그대로). 응답 시간은 충분히
짧지만, 크기가 3MB를 넘는다. 예매 액션마다 좌석맵을 다시 받아오므로 프론트에서 체감 비용이 된다.

## 결론과 후속 과제

- 2만 석 규모는 시딩 2초, 좌석맵 응답 130ms 안쪽으로 로컬 데모에 충분하다.
- 좌석맵이 전체 좌석을 한 번에 내려주는 구조는 좌석 수에 비례해 커진다. 응답 크기를 줄이는 방법
  (구역 단위 요청, 상태만 주는 델타 응답, 압축 등)은 별도 실험 과제로 남긴다.
- 경기 생성 시 좌석 전체를 복제하는 설계(DR-01)는 좌석 수가 늘면 경기 생성 비용이 같이 늘어난다.
  이 역시 v2 이후 판단 대상으로 남긴다.
